# 決定：發布時產生 version.json、tag 與 GitHub Release（2026-11-01）

## 結論
- `npm run release`（`scripts/release.mjs`）發布時，在 `gh-pages` 根目錄多放一個 `version.json`：
  `{ "version": "x.y.z", "releaseDate": "YYYY-MM-DD", "commit": "<來源 main 的完整 SHA>" }`
  - `version` 取自 `package.json`；`releaseDate` 是發布當下的**台北時間**日期；`commit` 是來源 `origin/main` 的 SHA。
  - 網址：`https://derliang.github.io/survey-feedback-helper/version.json`。只含版本資訊，不含任何學生資料。
- `--yes` 發布成功後，對來源 main commit 建立 annotated tag `v<版號>` 並 push，再用 `gh release create <tag> --verify-tag` 建立 GitHub Release，說明取自 `CHANGELOG.md` 的 `## [<版號>]` 區段。
- **tag 與 Release 失敗只警告，不擋發布**（站已上線，可事後手動補）。
- dry-run 會印出版號、將產生的 `version.json`、CHANGELOG 區段提示；push、tag、Release 一律只在 `--yes` 才執行。
- `--yes` 的額外門檻：`package.json` 版號必須是 `x.y.z` 且不是 `0.0.0`，本機與遠端都還沒有同名 tag（也就是每次發布前要先升版號）。

## 發布者的步驟（版號由人決定）
1. 在 PR 裡把 `package.json` 版號升到本次版本，並把 `CHANGELOG.md` 的 `[Unreleased]` 移成 `## [版號] - YYYY-MM-DD`。
2. 合併後在 `main` 上 `npm run release`（dry-run）確認，再 `npm run release -- --yes`。

## 被否決的做法
- 腳本自動改 `CHANGELOG.md`／`package.json` 並 commit：發布要求工作樹乾淨且 HEAD = `origin/main`，發布時再改檔會讓來源與已發布內容不一致。所以只做「區段提示」，由人在 PR 中改。
- 用 GitHub Actions 建 Release：專案規定不用 Actions（避免收費）。

## 給 Teacher Hub 的說明（由調度員轉告其對話；本專案不改 teacher-hub）
- `tools.json` 的 `versionJson` 填上面的網址；欄位 `version`、`releaseDate` 與 `commit` 可直接對應。
- `dateEvidence` 可指向該版本的 GitHub Release 或 tag `v<版號>`。
- 第一次發布前 `package.json` 還是 `0.0.0`，需先升版號（`--yes` 會擋 0.0.0），所以 `version.json` 不會出現 0.0.0。
