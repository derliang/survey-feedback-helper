# 決定記錄：技術選型、產品架構與發布規則（2026-10-30）

> 寫給沒看過討論的後來者。這份接續 [產品範圍與技術決定](2026-10-30-產品範圍與技術決定.md)，其中與本文衝突之處以本文為準（PDF 路徑、技術選型、Google 雲端硬碟）。
> 標示「暫定」者是 Claude 的建議、使用者採用但尚未實測；標示「使用者決定」者是使用者明確選擇。

## 一、硬規則（使用者要求，不得違反）

| 規則 | 內容 |
|---|---|
| 純網頁、免安裝 | 老師用瀏覽器開網址即可使用，不需安裝、註冊；沒有後端 |
| 全裝置可用 | 手機、平板、桌機各自設計版面與操作（mobile-first），不是把桌機縮小 |
| main 即上線 | 本專案 push／merge 到 `main` 就等於發布到 GitHub Pages 正式站。PR 階段必須測試完全通過，且使用者明確說「發布」才合併 |
| 全專案零費用 | Google API、字型、CDN、套件、部署都不得產生費用；引入前核對並登錄 `docs/third-party.md` |
| Google Cloud 不綁帳單 | Google Cloud 專案絕不綁定帳單帳戶，不啟用任何需要帳單的服務；只使用 Drive 與登入相關的免費 API |
| 資料不落地 | 原始問卷資料只在記憶體處理，關頁即清；瀏覽器只存設定、範本，以及檔案/資料夾的存取代號（不含資料內容） |
| 不蒐集使用數據 | 連匿名統計也不要 |

## 二、技術選型（使用者授權 Claude 以「最佳結果」決定，不因複雜度退讓）

| 層 | 選型 | 說明 |
|---|---|---|
| 語言／建置 | TypeScript + Vite | 輸出純靜態檔放 GitHub Pages；Node 建置只在開發端，老師端免安裝 |
| 介面 | Preact | 約 4KB，適合表單、精靈、編輯器等互動畫面 |
| 測試 | Vitest（單元）、Playwright（端對端、多解析度與觸控模擬） | 統計核心寫成不依賴瀏覽器的純函式模組 |
| xlsx 讀寫 | ExcelJS（MIT） | 能讀能寫、支援樣式，輸出才精美 |
| Word | docx（MIT） | 純前端產生 docx |
| zip | fflate（MIT） | 批次打包 |
| PDF | 程式直接產生（字型子集化） | 見下方 |
| 圖表 | 自製 SVG | 網頁、PDF、Word（轉 PNG）共用，風格由設計系統完全控制 |
| 設定儲存 | localStorage | 只存設定與範本 |
| 離線 | Service Worker（v1.0） | PWA |
| 部署 | GitHub Actions → GitHub Pages | 公開 repo 免費 |

套件授權均為 MIT／Apache-2.0，可併入 GPL-3.0；引入時逐一登錄。

## 三、核心架構：一份文件模型，多個輸出器

```
統計結果 + 範本(文件模型 JSON) → 預覽／編輯 → xlsx / Word / PDF
```

- 範本由「區塊」組成：標題、文字、統計表、圖表、留言區、老師評語、頁首頁尾、分隔線、圖片、分頁等；文字可用變數（如 `{姓名}`、`{平均分}`）。
- 預覽、PDF、Word 都由同一份文件模型輸出，所以編輯一次、格式一致。
- 範本存本機，隨設定匯出／還原，可分享。

## 四、線上編輯器（使用者決定）

- **層級二區塊編輯器＋高自由度功能**：直接在預覽上改文字、拖曳排序、增刪區塊、多欄、頁面大小與邊界、背景與頁框、圖片與 Logo、圖表顏色、變數、條件顯示（例如分數低於某值才顯示鼓勵語）、單一學生個別覆寫。
- **手機也提供完整編輯器**（使用者決定，Claude 原建議手機簡化）。做法：觸控專用設計——長按把手拖曳並保留上下按鈕、底部彈出屬性面板、預覽可縮放、編輯與捲動模式分開、觸控目標至少 44px、支援復原／重做。
- **誠實限制**：Word 不支援的效果在編輯器中標示。
- 版本拆分（暫定）：v0.2 文件模型、預設範本、輸出器；v0.3 完整編輯器。

## 五、PDF 路徑（使用者決定，修訂前份決定記錄）

- **程式直接產生為主**，字型子集化（只嵌入用到的字），批次一鍵輸出每位學生各一個 PDF 的 zip。
- 瀏覽器列印僅作桌機備用。
- 原因：手機的列印轉 PDF 體驗差，直接產生才能讓三種裝置輸出一致。

## 六、Google 雲端硬碟雙軌（使用者提議）

> 2026-10-31 修訂：軌二不再是獨立入口，併入「本機檔案」；軌一入口在設定頁。見[決定記錄](2026-10-31-頁面討論裁示.md)。

| | 軌一：使用者登入 | 軌二：原生檔案管理 |
|---|---|---|
| 做法 | Google 登入＋Drive API＋Picker | 裝置檔案/資料夾選擇器 |
| 桌機 | 所有瀏覽器 | Chrome／Edge 選「Google 雲端硬碟 for desktop」資料夾，直接讀寫，由桌面程式同步 |
| 手機／平板 | 可用 | 系統選檔視窗本來就列出 Drive |
| 版本 | v0.4 | 併入 v0.1 |

- Drive for desktop 內的 Google 原生格式（如表單回覆的 Google 試算表）只是捷徑，不能直接當 xlsx 讀，需先下載成 xlsx；軌一可自動處理。
- 軌一只申請 `drive.file`（僅限使用者選取或本程式建立的檔案），避免受限權限的付費資安評估與隱私風險。
- API 金鑰限制只能從 Pages 網址使用，並只開 Drive 與 Picker。
- 配額用完只會被拒絕、不會收費；介面顯示友善提示並建議改用軌二。
- 儲存位置抽象成「儲存提供者」：本機檔案、下載與上傳、系統分享、Google Drive API，依裝置自動選用。

## 八、PR 與發布關卡

PR 必須全部通過才能合併，並啟用 `main` 分支保護：

1. TypeScript 編譯與 lint
2. 單元測試（票數、同票抽籤、加權、去極端值、反向題等統計核心）
3. Playwright 端對端（多解析度、觸控模擬，用虛構資料）
4. 輸出檢查：xlsx、Word、PDF 內容與跑版（視覺比對）
5. 隱私掃描：repo 內不得有學生資料檔（xlsx／csv／docx／pdf 超出白名單即失敗）
6. 授權與費用檢查：新套件須與 GPL-3.0 相容並登錄、無費用
7. Google 權限檢查：程式碼與設定中出現 `drive.file` 以外的權限即失敗
8. 建置成功

流程：PR 全綠 → Claude 回報測試證據 → 使用者說「發布」→ 合併 → 確認 Pages 部署成功 → 回報正式站網址與 SHA。

**例外（使用者決定，2026-10-30）：純文件類可直接 push 到 `main`。** 原因：文件不是正式程式，直接進 `main` 才能讓後續對話一 pull 就拿到最新資訊。範圍僅限 `*.md`、`docs/`、`.github/` 範本與 `LICENSE`；碰到程式、workflow、設定或建置檔就走 PR。
連動待辦：建立部署流程時，要讓純文件變更不觸發重新部署，並讓分支保護對純文件變更放行（否則直接 push 會被擋）。尚未實作，目前沒有分支保護也沒有部署。

## 九、被否決或延後的選項

- 原生 JS 免建置：規模太大，會越寫越亂，測試與型別保護弱。
- Svelte：生態較小，與 docx、列印版面的搭配資料較少。
- 自由畫布（任意重疊、絕對定位）：Word 流動式排版無法精確對應，會跑版。
- 只做選項式：不符合「最大自由度」。
- 手機簡化編輯：使用者選擇手機也要完整編輯器。
- 只用列印轉 PDF：手機體驗差，批次不便。
- 只做 Google 登入或只做原生檔案管理：改為雙軌。
- OneDrive／Microsoft Forms：延後。
- 本機建置推 gh-pages 分支：改用 GitHub Actions。
- 蒐集錯誤報告：與零伺服器原則衝突。

## 十、未實測的風險與待驗證

- **手機完整編輯器**：設計與測試成本最高。Claude 沒有實體 iPhone／Android／平板可測，只能用裝置模擬；發布前需使用者或同事實機驗證，特別是 iOS Safari 的拖曳、鍵盤彈出與捲動。品質不如預期時回報並提出退路（暫時改簡化模式）。
- **PDF 中文字型子集化**：檔案大小、渲染品質尚未驗證；v0.2 前先做小型原型，並驗證「同一份文件模型輸出 Word 與 PDF」的一致性，結果不理想再回頭討論。
- **File System Access API**：Safari、Firefox 不可用，已規劃退回做法，尚未實測。
- **Google 免費配額與政策**：這是 Claude 的知識，v0.4 前須對照 Google 官方文件並留下來源連結。
- **學校 Google Workspace 可能限制第三方應用**：需使用者向資訊組確認，Claude 無法代為確認。
- **Google 表單匯出格式差異**（核取方塊題、格狀題等）與**效能上限**（回覆筆數、批次學生數）：v0.1、v0.2 用虛構樣本與壓力測試處理並寫入文件。

## 十一、Word 字型（使用者決定，2026-10-30，依[原型驗證結果](2026-10-30-原型驗證結果.md)）

- **Word 輸出使用系統字型**（Windows：微軟正黑體；macOS：PingFang TC），**不內嵌字型**。原因：docx 內嵌字型（含子集化）在實測的 Microsoft Word 上沒有生效，原因未明。
- **PDF 仍內嵌 Noto Sans TC 子集**，是最準確的版本；輸出設定與說明頁須標明「Word 版面可能與 PDF 有細微差異」。
- 被否決：整個字型內嵌（每份 4.2 MB）、繼續查內嵌失敗原因（不保證有結果）。
- 後續：改用系統字型後須重測 Word 與 PDF 的一致性（見 todo）。
