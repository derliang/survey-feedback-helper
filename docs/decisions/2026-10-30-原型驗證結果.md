# 決定記錄：技術原型驗證結果（2026-10-30）

> 寫給沒看過討論的後來者。驗證目標來自 [技術選型與發布規則](2026-10-30-技術選型與發布規則.md)〈十、未實測的風險〉：
> ①PDF 中文字型子集化的大小與品質　②同一份文件模型輸出 Word 與 PDF 的一致性　③整條流程能否在瀏覽器（含手機）執行。
> 原型程式在 [prototypes/pdf-docx/](../../prototypes/pdf-docx/)，**只用來驗證，不隨網站發布**。

## 結論

**可行。** 「同一份文件模型 → 程式直接產生 PDF 與 Word」在這個原型達到：

| 項目 | 結果 |
|---|---|
| 頁數一致 | Word 與程式 PDF 5/5 份相同（含一個項目被跨頁切開的情況） |
| 換行位置一致 | 134/134 行文字與斷行位置完全相同 |
| 位置偏差 | Word 相對程式版：垂直平均 0.39pt、最大 1.74pt（約 0.6 毫米）；水平平均 −0.68pt、最大 2.06pt |
| PDF 大小（含完整中文字） | 每份約 80 KB（最大 93 KB）；全班 35 份 2.8 MB |
| 不子集化的 PDF | 8.6 MB／份（約 100 倍），不可行 |
| 瀏覽器內執行 | 成功（Chrome 151）：35 位學生 PDF＋docx 共 2.9 秒，zip 4.5 MB，JS 記憶體 73 MB |
| 授權與費用 | 原型用到的所有套件皆為 MIT／BSD-3／Apache-2.0／0BSD／Zlib，免費，可併入 GPL-3.0 |

**但有條件**，下面「對正式版的決定」列出的做法必須遵守，否則會踩到原型踩過的坑。

## 驗證方法

- 用 35 位**虛構**學生、每人 1～2 頁的「報告回饋單」（標題、變數替換、評分表、長條圖、條列留言、頁尾頁碼）。
- 同一份文件模型分別交給 PDF 輸出器（pdf-lib）與 Word 輸出器（docx）。
- **Word 的實際排版用這台電腦的 Microsoft Word 輸出成 PDF**，再用 pdfjs 抽出兩份 PDF 每一行文字的位置逐行比對，並畫成並排圖用眼睛檢查。這比任何模擬都準，但只能在有 Word 的 Windows 上做。
- 瀏覽器端：esbuild 打包，Playwright 驅動 Chromium 實測。

## 發現的問題與對策（最重要的部分）

| # | 問題 | 影響 | 對策 |
|---|---|---|---|
| 1 | **pdf-lib 內建字型子集化會漏字**：中文字大多沒畫出來（墨跡只有完整字型的 29%），而且文字內容仍在 PDF 裡，所以「抽文字比對」完全看不出來 | 若沒有看圖就會誤以為 72 KB 的好成績，實際上 PDF 是壞的 | **改用 HarfBuzz（`subset-font`）先子集化，再以 `subset:false` 內嵌**。墨跡 100% 與完整字型一致。驗證 PDF 必須「看圖或比墨跡」，不能只比文字 |
| 2 | `subset-font` 主程式使用 Node 的 `fs`，**不能直接在瀏覽器用**；`fontverter` 需要 Node 的 `Buffer` | 正式版不能直接 `import` | 打包時修補「讀 wasm」那一行改用 `fetch`、補 `Buffer`、`fs`/`path` 換空模組（原型的 `browser/run-browser.mjs` 有寫法）。正式版建議自己包一層薄的 HarfBuzz 子集化模組，並把 wasm（約 0.7 MB）放進專案 |
| 3 | Word 輸出器對圖片段落設固定行高，Word 會**把圖裁掉** | 圖表上緣被切 | 文字段落用固定行高（EXACT）以求與 PDF 一致；**圖片段落改用最小行高（AT_LEAST）**，不可用固定行高 |
| 4 | 字型下載量大：Noto Sans TC 一般＋粗體各 6.8 MB（TTF），合計 13.6 MB | 手機首次載入太重 | 發布 **WOFF2**：各約 2.8 MB，合計 5.6 MB；以 Service Worker 快取（v1.0 PWA）。子集化工具可直接吃 WOFF2（但每次解壓很慢，見下方「待補」） |
| 5 | 這台的 Word 自動化（COM）**很容易卡住** | 只影響「用 Word 做回歸比對」這件事，不影響產品 | 見下方「Word 比對方法」 |
| 6 | 原型自己的 bug：變數替換的規則式只認英數（`\w`），不認中文 | `{姓名}` 沒被換掉 | 正式版變數名稱規則用 `[^{}]+`，並加單元測試 |

## 對正式版的決定（來自驗證，請連同前份決定記錄一併遵守）

1. **PDF 字型處理**：HarfBuzz 子集化後內嵌。每位學生、依字重（一般／粗體）**只子集化實際用到的字元**（原型：同一份用同字元子集 123 KB，依字重分開 84 KB）。**禁用 pdf-lib 內建的 `subset: true`**。
2. **PDF 驗證**：自動化測試要檢查「字形有畫出來」（例如比墨跡比例或渲染後與完整字型版比對），不能只抽文字。
3. **Word 輸出器的排版規則**（為了與 PDF 一致）：文字段落一律固定行高；表格列固定高度與欄寬；關閉寡行控制（`widowControl:false`）與中英自動間距（`autoSpaceEastAsianText:false`）；段落間距明確指定；圖片段落用最小行高；頁尾用頁碼欄位。這些限制要寫進文件模型的「Word 不支援或需限制的效果」清單，並在編輯器中標示。
4. **兩個輸出器各自排版**（PDF 用自己的換行與分頁引擎，Word 交給 Word 排），靠「固定行高、固定欄寬、相同的中文換行規則（行首禁則：，。、；：！？等不能在行首）」達到一致。原型的 PDF 換行引擎只實作了行首禁則、英數不拆開兩項，已足夠通過 134/134 行；其他規則（行尾禁則、標點擠壓、連字符號）尚未實作。
5. **圖表**：圖用 PNG（3 倍解析度）同時放進 PDF 與 Word，圖與版面一致。向量圖表（PDF 內畫線）可作為日後的優化，Word 仍須用 PNG。
6. **回歸測試分兩層**：(a) CI（GitHub Actions，無 Word）：文件模型→PDF 的快照、墨跡與換行檢查、docx 結構斷言；(b) 本機 Windows＋Word 的比對腳本（`compare.mjs`＋`export-word.ps1`），在改版面引擎或 Word 輸出器時手動跑。
7. **Word 檔字型（使用者 2026-10-30 要求先驗證內嵌；驗證失敗，策略待定）**：老師的電腦不一定有 Noto Sans TC。選項：(A) 內嵌整個字型：每份 docx 4.2 MB，太大，不採用；(B) 指定系統字型（Windows：微軟正黑體、macOS：PingFang TC），與 PDF 字型不同，換行位置可能不同，Word 與 PDF 不再保證一致；(C) 內嵌子集化字型。
   **(C) 的驗證結果：在這台 Word（Microsoft 365，Windows）沒有生效。** 做法：把子集化字型改名為系統不存在的「SFH Embed Test」（排除「系統剛好有同名字型」的干擾），用 docx 套件的 `fonts` 選項內嵌（每份 86 KB），讓 Word 排版成 PDF，檢查 PDF 用了哪個字型。結果 Word 一律退回微軟正黑體（有無內嵌輸出相同）。已排除的原因：①字元集欄位寫成文字（我的錯，已改用套件列舉，值為 `88`）②改名後的字型檔不合法（用 fontkit 驗證為合法，`fsType` 允許內嵌）③docx 套件的混淆（odttf）寫錯（還原後為合法 TTF，長度一致）④唯讀開檔（改用可編輯模式結果相同）。**原因未明**，可能是 Word 對內嵌字型的其他要求，下次可拿「Word 自己存出的內嵌字型 docx」當參考比對結構。
   **目前建議採 (B)**：Word 版指定系統字型，在輸出設定與說明頁標明「Word 版面可能與 PDF 有細微差異」；PDF 版仍是最準確的版本。是否改採 (B)、或再投入時間查 (C)，**待使用者決定**。重跑：`node exp-embed.mjs`、用 Word 輸出後 `node exp-embed-check.mjs`。

## 未驗證的部分（不要當成已驗證）

- **沒有實體手機／平板／Mac／Safari**。瀏覽器實測只有 Chromium，手機是用視窗大小＋CPU 降速模擬，Safari／iOS 的行為（記憶體上限、wasm、Canvas、下載行為）完全沒測。
- **只驗證了 Microsoft Word（Windows）的排版**。Word for Mac、LibreOffice、Google 文件、Pages 開同一份 docx 的結果沒測。
- 只用了 Noto Sans TC 的 Regular 與 Bold；罕用字、Emoji、簡體字、日文假名、直排、雙欄、頁首頁尾變化、超長表格跨頁、圖文環繞都沒測。
- 版面只有一種範本（報告回饋單）；個人回饋單的其他版面、班級總表（大表格）沒測。
- 效能只測了 35 人；全班 40 人以上、每人多頁、留言很長時的上限沒測。
- 瀏覽器測試的字型是從本機伺服器讀取，**不代表真實網路下載時間**。
- 圖表只做了一種長條圖。

## Word 比對方法（本機驗證用，已知很容易卡住）

這台 Word 的自動化（COM）常卡住，原因未明。**實測有效、可重現的做法**（缺一不可）：
1. 在 PowerShell 用 `Start-Job -ScriptBlock { … }`（**整段寫在指令裡**，不要用 `-FilePath` 腳本檔），並用 `Wait-Job -Timeout` 設逾時；
2. Word 設為**可見**（`Visible = $true`）；隱藏模式會卡；
3. 只用 `Documents.Open(路徑, $false, $true)` 加 `SaveAs2(路徑, 17)`；**不要**呼叫 `ComputeStatistics`、`ExportAsFixedFormat`；
4. 結束後只清理**自己啟動的** Word（命令列含 `/Automation`），不碰使用者原有的 Word。

範例見 [prototypes/pdf-docx/export-word.ps1](../../prototypes/pdf-docx/export-word.ps1) 開頭的註解。

## 重跑方式

```
cd prototypes/pdf-docx
npm install
node run.mjs 35            # 產生全班 PDF 與 docx，輸出大小與時間
node exp-subset.mjs        # 三種字型子集化方式的對照
node browser/run-browser.mjs 35 ttf 1 0   # 瀏覽器實測（人數 字型格式 CPU降速倍率 手機視窗0|1）
node compare.mjs 01 02 09 18 27           # 需要先用 Word 輸出 output/wordpdf/*.pdf
```

輸出在 `prototypes/pdf-docx/output/`（已被 `.gitignore` 擋下，不會進版控）。需要本機已安裝 Noto Sans TC（預設讀 `C:/Windows/Fonts`，可用環境變數 `PROTO_FONT_DIR` 改）。

## 手機等級效能（CPU 降速 4 倍、手機視窗、WOFF2）

**未完成。** 第一次（每位學生都重新解壓 WOFF2）跑了十幾分鐘仍無結果，被我中止；第二次（字型只解壓一次）約 5 分鐘無結果時被我中止。無法判斷是「真的卡住」還是「降速 4 倍下就是很慢」，**不要據此下結論**。已知的是：同一份流程在桌機 Chrome 不降速、TTF 字型只要 2.9 秒（35 人）。下次要查：①WOFF2 解壓（wawoff2 的 wasm）在瀏覽器的耗時 ②用 TTF 字型加降速重測，把字型解壓與子集化的耗時分開量。
