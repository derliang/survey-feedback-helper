# 決定記錄：Pages 改本機發布，不用 GitHub Actions（2026-11-01）

## 決定（使用者 2026-11-01）

1. 不使用 GitHub Actions（擔心收費）。刪除 `.github/workflows/deploy.yml`、`pr-gate.yml`。
2. GitHub Pages 設定為「從 `gh-pages` 分支部署」，網站 https://derliang.github.io/survey-feedback-helper/ 已上線。
3. 發布由本機 `npm run release` 完成：先跑 `npm run ci`，全綠才把 `dist/`（加 `.nojekyll`）以**新 commit** 更新 `gh-pages`。未加 `--yes` 只做 dry-run。使用者說「發布」後才加 `--yes`。
4. 原 PR 關卡（型別、lint、單元、隱私、授權、Google 權限、建置、效能預算、e2e）全部保留，由 `npm run ci` 在本機依序執行，結果貼在 PR 的測試證據。

## 為什麼 `main` 不再當 Pages 來源

- `main` 一 push 就上線，讓純文件直接 push、分支保護、部署觸發條件全綁在一起，需要 `paths-ignore` 與 ruleset 例外；而且沒有 CI 就沒有東西能在上線前擋住壞掉的建置。
- 分開後：`main` 只是原始碼，`gh-pages` 只是建置產物。`main` 可隨時合併、推文件；上線是另一個有意識的動作（`--yes`）。
- `gh-pages` 的每個 commit 訊息記錄來源 `main` SHA，可追溯、可回滾（再發布舊的 main）。

## 為什麼不用 Actions

使用者擔心收費。公開 repo 的標準 runner 目前免費，但規則可能改，且「全專案零費用」是硬規則；本機一台電腦就能做到同樣的檢查，沒有理由承擔風險。代價：沒有雲端強制關卡，要靠 PR 附本機證據與使用者的「發布」口令把關；兩台電腦各自跑，需要 Node 24 與 Playwright Chromium。

## 被否決的選項

- 繼續用 Actions 部署（`deploy.yml`，2026-10-30 的決定）：同上，被使用者推翻。
- 把 `main`（或 `/docs`）當 Pages 來源：需把建置產物 commit 進 `main`，污染歷史，且「合併即上線」。
- 強制覆寫 `gh-pages`（`push --force`）：會丟歷史、無法回溯；改為每次新增 commit，遠端有人搶先時 push 被拒絕而不是蓋掉。
- 用 `gh-pages` npm 套件：新增套件要核對授權、登錄；自寫腳本約百行即可，不引入相依。

## 腳本行為（scripts/release.mjs）

- 要求工作樹乾淨。`--yes` 時另要求 HEAD = `origin/main`，且不得 `--skip-ci`。
- 在系統暫存目錄用 `git worktree` 取出 `gh-pages`（沒有則建 orphan），不動主工作目錄；結束後移除。
- 內容與現有 `gh-pages` 相同就不 commit。署名 `Claude-desktop`／`Claude-laptop`（依主機名）。
- push 後 fetch 並比對遠端 SHA，不一致即報錯。

## 連動
