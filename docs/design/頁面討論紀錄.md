# 頁面討論紀錄

> 用途：使用者看設計稿（以桌機畫面為主）逐頁指出要修改的地方時，在這裡記下「要改什麼、設計稿怎麼改、程式要怎麼實作」。
> **這份檔案只記錄，不施工。** 記錄的對話不改設計稿、不改 `DESIGN.md`、不寫程式；使用者日後另開對話，依這份紀錄施工。
> 規範的唯一來源仍是 [DESIGN.md](DESIGN.md)；功能藍圖見 [docs/feature-blueprint.md](../feature-blueprint.md)。

## 給記錄者（接手的對話）看的規則

1. **只記錄與 push**：使用者說「記下來」或每頁討論完時，一次寫進本檔。不順手改模擬頁、產生器、`DESIGN.md`、`tokens.css`。
2. **使用者的話與我的推論分開**：「使用者意見」欄寫原話或忠實轉述；推論、建議一律放「我的建議」，標明尚未獲使用者同意。
3. **寫給沒看過這段對話的人**：每筆都要看得懂，不能只寫「同上」「照剛剛說的」。
4. **畫面用編號加中文名稱**，例如 `D19 報告回饋欄位對應`。編號對照見 `build/list.mjs` 與成品頁的桌機分頁。
5. **連動要寫全**：使用者的修改通常牽動多個功能。要列出會連動的其他畫面（手機、平板、桌機各自是哪幾個）、輸出文件、統計規則、設定與專案檔。
6. **被否決的方案與原因要留**，免得後人重提。
7. **不寫真實學生資料**；範例一律虛構。
8. 與已定案的硬規則（專案 `CLAUDE.md`）或決定記錄衝突時，在該筆「風險與衝突」欄標出，不自行解決。
9. 純文件可直接 push 到 `main`；分批 push，省額度。commit 署名依全域規範。

## 狀態說明

| 狀態 | 意思 |
|---|---|
| 待討論 | 使用者提到了，但結論還沒定 |
| 已定案，待改設計 | 使用者同意了做法，設計稿尚未修改 |
| 設計已改 | 模擬頁、`DESIGN.md`、成品頁都已更新 |
| 待實作 | 設計已定案，等程式施工（專案骨架建好之後） |
| 已實作 | 程式完成並通過測試 |
| 已否決 | 不做；原因寫在該筆 |
