> 首屏最新一次重測 2026-11-07（見下）；其餘量測日期 2026-11-01，桌機（Deskmini_B760）上同時有其他對話在跑，數字有雜訊；當作量級看，不當保證。

## 首屏載入（硬規則 9）

- **首頁程式大小**：76.4 KB gzip（2026-11-04 起；之前 86.6 KB；預算 150 KB，`npm run check:budget` 每次 CI 檢查）。

- **首屏時間**（`node scripts/measure-first-screen.mjs`，先 `npm run build`；手機視窗 390×844、CPU 降速 4 倍、關閉 Service Worker 即第一次造訪；量到「首頁主標題出現」）：

  **2026-11-04 瘦身後**（PR：`perf/lazy-routes` 同批；量測腳本改為預設像 GitHub Pages 一樣 gzip，`GZIP=0` 可量未壓縮）：統計、輸出、準備資料、方法說明四個畫面改為進入時才載入（`src/ui/lazy-view.tsx`），首頁入口 `index` 從 127 KB 降到 47 KB（未壓縮）。桌機模擬 Slow 4G（4× 降速）三次：1.67／1.69／1.73 秒與 1.67／1.68／1.69 秒，**中位數約 1.68 秒（之前 2.10 秒）**；Fast 4G 中位數 0.61 秒。已低於 2 秒目標；仍是模擬，**真機未量**。

  **2026-11-07 重測（`main` 837c835 起、PR #66 載入速度優化之後；桌機 Deskmini_B760，Node 24）**：`npm run check:budget` 首頁合計 **76.4 KB gzip**（預算 150 KB，與 11-04 相同，入口 `index` 47.0 KB 未壓縮，沒有退步）。首屏時間（同上腳本、手機 390×844、CPU 4× 降速、第一次造訪、gzip；每組三次，括號為中位數）：

  | 情境 | 各組結果（ms） | 中位數落在 |
  |---|---|---|
  | Slow 4G | 1898／1987／1991（1987）；1784／1835／1866（1835）；2034／2430／2493（2430）；2231／2252／3439（2252）；未壓縮 1767／1804／1827（1804） | 約 1.8～2.4 秒 |
  | Fast 4G | 1161／1201／2035（1201）；847／895／931（895）；791／805／1092（805） | 約 0.8～1.2 秒 |

  **這次的數字有雜訊**：量測時同機有另外四個對話在跑建置與 e2e（CPU 吃重），同一組設定的三次中位數就差到 0.6 秒，所以 11-04 量到的 Slow 4G 1.68 秒、Fast 4G 0.61 秒**沒有在這次重現，也不能據此說退步**（程式大小沒變）。可信的結論只有：程式大小仍在預算內且與 11-04 相同；模擬 Slow 4G 在機器不忙時約 1.7～1.9 秒，機器忙時會到 2.2～2.4 秒；Fast 4G 穩定低於 1.2 秒。要拿到乾淨數字，須在沒有其他程式吃 CPU 時重跑。**真機仍未量，待使用者用手機量**（步驟見 [real-device-checklist.md](real-device-checklist.md)）。

  舊結論（瘦身前）：中階手機（4× 降速）在 Fast 4G 以上達成「首屏 2 秒內」；Slow 4G 的**第一次**造訪略超過，之後有 Service Worker 與瀏覽器快取就快很多。這個腳本不進 `npm run ci`（受機器負載影響會誤報）。**調度員 2026-11-01 決定：Slow 4G 第一次造訪略超過 2 秒先接受。** **沒量到的**：真機（見 [real-device-checklist.md](real-device-checklist.md)）。

## 統計計算壓力測試

`src/core/perf.test.ts`（隨 `npm test` 跑，上限設得很寬，只當「不要退步」的護欄）。實測耗時：

| 同上 | 3000 種書名 | 約 20 秒 |

### 上限與建議

- 班級規模（數十到數百份回覆）所有計算都在眨眼之間，不需要顧慮。
- **實際的瓶頸是「資料檢查的書名多種寫法」**：它把每兩種書名兩兩比對，時間隨「不同書名種數」平方成長。一個班不會有上千種書名，但若有人把幾千筆開放式文字欄誤標成書名，檢查會卡住十幾秒。建議上限：**不同書名 ≤ 1000 種**。需要時可再最佳化（先依長度或二字組分桶，再比對）。**調度員 2026-11-01 決定：不最佳化，上限 1000 種寫入使用說明**，因為實際使用碰不到。
- 其餘計算在 20 萬份回覆內都在數秒內；超過一萬份回覆的 Excel 檔，瓶頸會先落在讀檔（xlsx 解壓）與畫面渲染，不在統計。
- 這些都是在 Node 上量的，手機瀏覽器可能慢 3～5 倍，上表仍有一個量級的餘裕。
