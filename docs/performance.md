# 效能紀錄與上限

> 量測日期 2026-11-01，桌機（Deskmini_B760）上同時有其他對話在跑，數字有雜訊；當作量級看，不當保證。

## 首屏載入（硬規則 9）

- **首頁程式大小**：86.6 KB gzip（預算 150 KB，`npm run check:budget` 每次 CI 檢查）。
- **進入輸出頁才載入**：xlsx／docx／PDF 與字型延遲載入；輸出頁一開就呼叫 `registerAssetCache()`（`src/ui/views/OutputView.tsx`），Service Worker 把字型與 wasm 快取起來，之後離線也能輸出。
- **首屏時間**（`node scripts/measure-first-screen.mjs`，先 `npm run build`；手機視窗 390×844、CPU 降速 4 倍、關閉 Service Worker 即第一次造訪；量到「首頁主標題出現」）：

| 網路情境 | 三次結果 | 中位數 |
|---|---|---|
| Fast 4G（約 9 Mbps、40 ms，`PROFILE=fast`） | 1.59／1.85／1.89 秒 | 1.85 秒 |
| Slow 4G（約 1.6 Mbps、150 ms，預設） | 2.07／2.08／2.10 秒（一次）；2.54／3.53／3.78 秒（另一次，機器忙時） | 2.1～3.5 秒 |

  結論：中階手機（4× 降速）在 Fast 4G 以上達成「首屏 2 秒內」；Slow 4G 的**第一次**造訪略超過，之後有 Service Worker 與瀏覽器快取就快很多。這個腳本不進 `npm run ci`（受機器負載影響會誤報）。**調度員 2026-11-01 決定：Slow 4G 第一次造訪略超過 2 秒先接受。** **沒量到的**：真機（見 [real-device-checklist.md](real-device-checklist.md)）。

## 統計計算壓力測試

`src/core/perf.test.ts`（隨 `npm test` 跑，上限設得很寬，只當「不要退步」的護欄）。實測耗時：

| 情境 | 規模 | 耗時 |
|---|---|---|
| 報告回饋彙整 | 2 萬份回覆、400 位被評對象、8 題 | 約 0.1 秒 |
| 報告回饋彙整（含去極端值） | 20 萬份回覆、2000 位被評對象 | 約 1.3 秒 |
| 評分統計 | 50 萬格 | 約 0.4 秒 |
| 複選題統計 | 20 萬格、5 個選項 | 約 0.8 秒 |
| 資料檢查 | 1 萬份回覆、200 種書名 | 約 0.2 秒 |
| 讀 csv | 5 萬列 × 10 欄 | 約 0.25 秒 |
| 資料檢查，**書名全部不同** | 1000 種書名 | 約 1.8 秒 |
| 同上 | 3000 種書名 | 約 20 秒 |

### 上限與建議

- 班級規模（數十到數百份回覆）所有計算都在眨眼之間，不需要顧慮。
- **實際的瓶頸是「資料檢查的書名多種寫法」**：它把每兩種書名兩兩比對，時間隨「不同書名種數」平方成長。一個班不會有上千種書名，但若有人把幾千筆開放式文字欄誤標成書名，檢查會卡住十幾秒。建議上限：**不同書名 ≤ 1000 種**。需要時可再最佳化（先依長度或二字組分桶，再比對）。**調度員 2026-11-01 決定：不最佳化，上限 1000 種寫入使用說明**，因為實際使用碰不到。
- 其餘計算在 20 萬份回覆內都在數秒內；超過一萬份回覆的 Excel 檔，瓶頸會先落在讀檔（xlsx 解壓）與畫面渲染，不在統計。
- 這些都是在 Node 上量的，手機瀏覽器可能慢 3～5 倍，上表仍有一個量級的餘裕。
